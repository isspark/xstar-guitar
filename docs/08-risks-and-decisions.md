## 2. 产品假设

| ID | 假设 | 验证方法 | 失败后的调整 |
|---|---|---|---|
| H-01 | 用户愿意先调音再学习 | 首次使用观察与漏斗 | 允许先体验课程，调音在首次演奏前强提示 |
| H-02 | 微课+练习优于长视频 | 5 至 8 名可用性测试与完成率 | 缩短内容、增加示范、调整步骤密度 |
| H-03 | 5 至 8 个和弦足够完成首批曲目 | 课程/曲目内容审查 | 选择更简单曲目或扩展 1 至 2 个和弦 |
| H-04 | 用户接受自评练习 | 访谈、退出率、反馈 | 增加更清晰自检或有限单音检测 |
| H-05 | PDF/图片是主要导入格式 | 内测导入格式统计（本地/自愿） | 调整 MusicXML/文本格式优先级 |
| H-06 | 五项一级导航可理解 | 原型走查 | 合并练习到学习，改为四项 |
| H-07 | 在线免费资源能形成合规来源 | API/条款/许可评审 | 首发只保留接口与外部链接，不承诺内置搜索源 |

## 3. ADR

### ADR-001：本地优先且免登录

- 状态：已接受。
- 决策：核心工具、课程、练习、进度和导入无需账号及网络。
- 理由：降低首次门槛、服务练琴场景、减少隐私和后端复杂度。
- 后果：暂时没有跨设备同步；后续同步必须保持免登录路径。

### ADR-002：原生 Kotlin + Compose

- 状态：已接受。
- 决策：首发采用原生 Android 和全 Compose UI。
- 理由：需要深入控制 AudioRecord、AudioTrack、Media3、SAF 和自适应窗口。
- 后果：短期不共享 iOS UI；纯领域与 DSP 模块避免 Android 耦合，为未来复用保留可能。

### ADR-003：Navigation 3 与 SceneStrategy

- 状态：已接受。
- 决策：类型安全 NavKey；列表详情和支持面板使用 Material Navigation 3 SceneStrategy。
- 理由：统一手机与大屏导航状态，避免两套页面/导航。
- 后果：工程启动时需确认官方推荐版本并跟踪 API 演进。

### ADR-004：Room 是结构化业务事实来源

- 状态：已接受。
- 决策：课程索引、进度、练习、乐库和许可存 Room；设置存 Proto DataStore。
- 理由：事务、关联、FTS、Flow 和迁移需求明确。
- 后果：必须导出 Schema 并维护全路径 Migration Test。

### ADR-005：大文件不存数据库

- 状态：已接受。
- 决策：PDF、图片、媒体和解析缓存存应用私有目录，Room 只存元数据。
- 理由：避免数据库膨胀和 BLOB 内存问题。
- 后果：必须实现数据库与文件的补偿事务和孤立清理。

### ADR-006：默认复制 SAF 导入

- 状态：已接受。
- 决策：导入文件默认复制至应用私有目录。
- 理由：源文件移动、删除或授权撤销后仍可离线使用。
- 后果：占用额外空间，需要存储管理；链接模式后置。

### ADR-007：调音器使用独立 AudioRecord + DSP

- 状态：已接受。
- 决策：DSP 核心纯 Kotlin，平台采集单独实现。
- 理由：Media3 不适合实时麦克风音高分析，纯 Kotlin 易于确定性测试。
- 后果：需要专门处理设备、线程、泛音和置信度问题。

### ADR-008：节拍器使用 AudioTrack 音频帧时间线

- 状态：已接受。
- 决策：连续生成 PCM，以输出帧位置调度拍点和视觉反馈。
- 理由：避免 Timer、Handler、Coroutine delay 和 UI 帧造成抖动与漂移。
- 后果：实现更复杂；只有测量证明不足时才升级 Oboe。

### ADR-009：麦克风 PCM 默认不持久化

- 状态：已接受。
- 决策：实时 PCM 只在内存中处理，不保存、不上传、不记录。
- 理由：隐私最小化，当前产品不需要回放。
- 后果：无法离线重算；未来录音功能需独立同意和新 ADR。

### ADR-010：在线资源使用可替换 Provider

- 状态：已接受。
- 决策：供应源必须通过 API、许可、缓存、署名、撤回和隐私准入。
- 理由：避免绑定不稳定、未经授权的网页抓取。
- 后果：在来源审核完成前只用 Fake Provider；在线搜索可晚于本地 MVP。

### ADR-011：课程步骤为受控版本化类型

- 状态：已接受。
- 决策：内容使用可校验的结构化步骤，不执行任意脚本。
- 理由：离线、安全、可迁移并支持构建期校验。
- 后果：新增交互步骤可能需要客户端发布或内容引擎升级。

### ADR-012：自动演奏评分后置

- 状态：已接受。
- 决策：MVP 使用调音检测、节拍目标、计时和用户自评，不判断完整和弦演奏。
- 理由：复杂和弦和节奏误判会破坏新手信任，样本与算法成本高。
- 后果：学习结果证据有限；先通过清晰自检和可用性验证弥补。

## 4. 需在 Phase 0 决定

- 最低 Android SDK 与目标 SDK。
- 首发是否支持 MusicXML/MXL，或只支持 PDF、图片和受控文本。
- 调音采样率、窗口、阈值和 AudioSource 基线。
- 节拍器后台行为及是否首版支持震动。
- 一级导航采用四项还是五项。
- 首批 3 至 5 首曲目及每首许可依据。
- 第一个生产在线 Provider 是否满足准入；不满足时是否仅发布本地搜索和外部链接。

## 5. 变更流程

新决策应包含状态、上下文、选择、理由、替代方案和后果。替换旧 ADR 时保留旧条目并标记 superseded。影响 MVP 的决策同时更新 PRD、Roadmap、测试策略和 Backlog。
